# 세 기능 프론트 UI와 백엔드 연결 메모

현재는 프론트 개발과 중간 발표를 위한 임시 명세입니다. 새 엔드포인트와 필드명은 AI/백엔드 파트의 최종 합의가 아닙니다. 참고 자료는 W3 발표자료의 서비스 개요·시나리오(6~13쪽)입니다. 사용자의 최신 요구에 따라 온도계는 상대가 아닌 **현재 사용자 나(A)**만 표시합니다.

팀원에게 전달할 구현 순서·협의 표·사용 방법은 [백엔드 구현 인계 가이드](backend-implementation-handoff.md), Codex/Claude Code에 붙여넣을 요청문은 [구현 요청문](backend-agent-prompt.md)에 있습니다.

추가 후보인 [Jev 상대 반응 미리보기](../backend/docs/jev-recipient-preview-proposal.md)는 미전송 초안을 받은 상대의 예상 감정·강도를 표시하는 별도 기능입니다. 아래의 나(A) 온도계 계약을 변경하지 않으며, 새 API·타입·UI와 기능별 모드 설계는 아직 구현되지 않았습니다.

## 실행 모드

`frontend/.env`:

```dotenv
EXPO_PUBLIC_API_URL=http://127.0.0.1:8000
EXPO_PUBLIC_API_MODE=local
EXPO_PUBLIC_FEATURE_MODE=mock
```

| 설정 | 값 | 동작 |
|---|---|---|
| 채팅 전송 `API_MODE` | `local` (기본) | 프론트 로컬 메시지 추가, HTTP 없음 |
| 채팅 전송 `API_MODE` | `receipt` | 기존 `POST /v1/demo/messages`, 입력 수신 확인 |
| 채팅 전송 `API_MODE` | `ai` | 기존 `POST /v1/messages/analyze`, 실제 AI 분석 |
| 기능 `FEATURE_MODE` | `mock` (기본) | 순화/온도계/판결은 프론트 예시. AI 호출 없음 |
| 기능 `FEATURE_MODE` | `api` | 순화는 기존 API, 온도계·판결·반론은 아래 제안 API 호출 |

두 모드는 독립입니다. 중간 발표에서 입력의 서버 전달까지 보여주려면 `receipt + mock`을 사용할 수 있습니다. 기본 `local + mock`은 백엔드 없이 실행 가능합니다. `api`로 바꿔도 아직 없는 기능 서버가 생기지는 않습니다. 온도계/판결/반론은 구현 전에는 404로 실패합니다. API 실패를 예시 결과로 바꾸지 않고 오류와 재시도를 제공합니다.

Expo 개발 서버(8081)는 앱 코드를 제공하고 FastAPI(8000)는 HTTP/JSON API를 제공합니다. 개발 중에는 각각 실행하며, 프론트에서 백엔드를 호출합니다. 모바일 배포 후에는 Expo 개발 서버 없이 앱이 배포된 API 주소를 호출합니다. 웹은 같은 도메인에 함께 배포할 수도 있습니다.

## 화면과 시연 순서

1. 웹의 휴대폰 프레임 바깥 관리자 패널에서 **예시 대화로 바꾸기**: `/chat`으로 이동하고 현재 대화를 룸메이트 청소 갈등 4개 발화로 교체하며 순화 초안을 채웁니다. 이전 판결과 쿨다운도 초기화합니다.
2. 언어 순화 ON: 초안 입력이 600ms 멈추면 확인하고, 필요할 때 **대안 보기**를 표시합니다. 보내기에서도 확인한 후 대안/원문/직접 수정 중 하나를 선택합니다.
3. 감정 온도계 ON: 메시지 또는 관계가 변경되면 최근 최대 10개 메시지로 나(A)의 상태를 갱신합니다. 3단계 이상에서는 쿨다운 패널을 열 수 있습니다.
4. **다툼판결 요청** → `/verdict`: 모드·전달할 대화·추가 상황을 확인하고 요청합니다. 진행 → 양쪽 점수·요약·제안·공개 토론 로그 → 반론 제출 흐름입니다.
5. `/settings`: 기능 ON/OFF, 순화 민감도, 관계를 제공합니다. 서버 연결 확인과 A/B 화자 전환은 바깥 관리자 패널에서 합니다.

대화/초안/입력 화자/기능 설정/판결 결과는 앱 실행 중 메모리에서 유지되고 새로고침 시 초기화됩니다. 관리자 패널의 A/B 선택은 한 기기에서 상대 발화를 재현하기 위한 버튼입니다. 실제 로그인 사용자 매핑이나 다른 기기와의 메시지 전송은 없습니다.

웹의 앱 영역은 440×956 논리 크기로 표시하며 프레임 전체를 창 크기에 맞춰 축소합니다. 관리자 패널의 100% 옵션은 원래 크기입니다. 관리 도구는 넓은 창에서는 오른쪽, 좁은 창에서는 프레임 아래에 놓이고 실제 모바일 앱에는 표시하지 않습니다. 순화/쿨다운 팝업은 웹에서도 앱 프레임 안에 표시합니다. 이는 UI 시연 도구이며 관리자 인증/서버 권한 기능은 없습니다.

## 1. 언어 순화

### UI 규칙

- ON이며 나(A)가 작성한 초안만 확인합니다. OFF 또는 상대(B) 시연 입력은 확인 요청 없이 전송합니다.
- 메시지 목록에는 선택한 최종 문장만 추가합니다. 초안 확인 자체는 메시지 전송이 아닙니다.
- 표현이 안전하면 바로 전송하고, 대안이 필요하거나 판단이 불확실하면 패널에서 사용자의 선택을 기다립니다.
- 원문 전송과 직접 수정 경로를 유지합니다. 실패한 경우에도 자동 전송하지 않습니다.
- 입력/관계/최근 대화/민감도가 바뀌면 이전 요청을 취소하고 이전 결과를 새 초안에 적용하지 않습니다.
- 민감도 0.25/0.5/0.75는 임시 UI 값입니다. 관계별 자동 계산은 없습니다.

### 이미 있는 API: POST /v1/drafts/analyze

기존 `ConversationInput`에 `suggest_rewrite: true`를 추가합니다. 최근 대화는 초안을 제외한 최대 10개이고, `previous_temperature`는 기존 대화 전체 갈등 점수입니다. 민감도는 백엔드가 받지 않으므로 현재 어댑터에서 제외합니다.

```json
{
  "recent_messages": [{ "speaker": "B", "text": "오늘은 못 했어." }],
  "speaker": "A",
  "text": "진짜 대단하시네 ㅋㅋ 맨날 그 모양이지",
  "relationship": "룸메이트",
  "previous_temperature": 0,
  "suggest_rewrite": true
}
```

화면 변환:

| 백엔드 `decision` | 화면 `decision` | 처리 |
|---|---|---|
| `rewrite_suggested` | `suggested` | `rewritten_text`가 있으면 대안 1개로 표시 |
| `below_threshold` | `safe` | 최종 전송 가능 |
| `low_confidence` | `uncertain` | 판단 불확실 안내, 원문/수정 선택 |

기존 응답의 `features.rationale`는 설명으로 표시합니다. 현재 API는 대안을 최대 **1개** 반환하며 UI는 시연에서 **3개**를 보여줍니다. 대안 여러 개를 지원하려면 `alternatives: string[]` 확장이 필요합니다. 서버 민감도 적용과 초안 확인 실패 정책은 팀 합의가 필요합니다. 입력 중 확인은 실제 AI 모드에서 비용이 발생할 수 있으므로 호출 주기도 합의해야 합니다.

## 2. 나의 감정 온도계

기존 `/v1/messages/analyze`의 `temperature`(대화 전체 0~100)는 나의 감정 1~5가 아닙니다. 임의로 변환하지 않습니다. 별도 감정 응답이 필요합니다.

### 제안: POST /v1/emotions/analyze — 아직 미구현

```json
{
  "speaker": "A",
  "relationship": "룸메이트",
  "recent_messages": [
    { "speaker": "A", "text": "지난번에도 그래서 좀 답답해." },
    { "speaker": "B", "text": "내일은 같이 할 수 있을 것 같아." }
  ]
}
```

제안 응답:

```json
{
  "subject": "A",
  "level": 3,
  "trend": "up",
  "recommendation": "잠시 쉬면서 내가 원하는 점을 정리해보세요.",
  "contextCount": 2
}
```

- `level`: 1 평온 / 2 주의 / 3 경고 / 4 위험 / 5 폭발. 심리 확률이나 의료 진단으로 해석하지 않습니다.
- `subject`: 분석 대상 사용자. 현재는 고정 A이며 요청 화자와 응답 대상이 다르면 거절합니다.
- `trend`: `up | flat | down`. 백엔드가 이전 감정 상태를 보관할지 최근 대화에서 계산할지 합의해야 합니다.
- `contextCount`: 분석에 사용한 메시지 개수. 초안이 아니라 이미 전송된 발화가 포함됩니다.
- ON일 때 대화 변경 후 갱신하며 OFF면 요청/표시를 중단합니다. 상대의 감정 점수나 대화 전체 점수를 표시하는 UI가 아닙니다.
- 쿨다운은 사용자 선택입니다. 3분 타이머가 끝나도 자동 전송하지 않으며 직접 해제할 수 있습니다.

## 3. 다툼판결과 반론

### 제안: POST /v1/verdicts — 아직 미구현

```json
{
  "room_id": "presentation-room",
  "requester": "A",
  "mode": "WWE",
  "relationship": "룸메이트",
  "recent_messages": [
    { "speaker": "A", "text": "오늘 청소 같이 하기로 했잖아." },
    { "speaker": "B", "text": "미안, 오늘 너무 바빠서 못 했어." }
  ],
  "context": "이번 주 청소는 상대 차례였어요."
}
```

요청 시점의 최대 10개 메시지를 복사해서 고정합니다. 추가 상황은 선택이며 UI 최대 1000자입니다. 양쪽 발화가 없으면 요청 버튼을 비활성화합니다. `room_id`는 시연 상수이며 실제 방 ID가 아닙니다.

제안 응답:

```json
{
  "verdictId": "verdict-123",
  "mode": "WWE",
  "plaintiff": {
    "logic": 72,
    "emotionControl": 45,
    "evidence": 80,
    "strength": "구체적인 약속을 짚었습니다.",
    "improvement": "일반화하는 표현을 줄여보세요."
  },
  "defendant": {
    "logic": 50,
    "emotionControl": 78,
    "evidence": 35,
    "strength": "사정을 설명했습니다.",
    "improvement": "약속 변경을 먼저 알려주세요."
  },
  "summary": "양쪽 입장과 책임을 정리한 요약",
  "recommendation": "다음 대화를 위한 구체적인 제안",
  "humor": "상황에 맞는 유머 한 줄",
  "debateLog": [
    { "role": "prosecutor", "round": 1, "text": "공개할 검사 발언" },
    { "role": "defense", "round": 1, "text": "공개할 변호사 발언" },
    { "role": "factcheck", "round": 1, "text": "공개할 사실 확인" },
    { "role": "judge", "round": 1, "text": "공개할 판사 발언" }
  ]
}
```

현재 화면에서 `plaintiff`는 A(나), `defendant`는 B(상대)로 고정 매핑합니다. 실제 요청자/원고/피고/로그인 사용자 ID 매핑은 합의가 필요합니다. 점수는 항목별 0~100이며 심리 온도와 다릅니다. 토론 로그는 사용자에게 공개할 설명/발언만 받습니다. 모델 내부 추론 기록은 필요하지 않습니다.

WWE/UFC는 발표자료의 명칭을 UI에 반영했습니다. 실제 에이전트 구성, 정지 조건, 유머 수준, 점수 정책은 확정하지 않았습니다. 예시에서 모드에 따라 안내/유머만 바뀝니다.

### 제안: POST /v1/verdicts/{verdictId}/appeals — 아직 미구현

```json
{ "text": "지난 두 번도 내가 대신 청소했어요." }
```

응답은 판결과 같은 형식입니다. UI 최대 2000자이며 공백 반론은 제출하지 않습니다. 서버는 판결 ID로 원래 대화와 이전 판결을 조회해야 합니다. 재판결이 새 ID를 만들지, 이전 반론을 누적할지, 횟수 제한/비용을 어떻게 처리할지는 합의 대상입니다. 프론트 예시는 원래 요청의 대화를 유지하고 반론 결과 화면만 재현합니다.

현재 어댑터는 HTTP 응답으로 전체 결과를 받는 방식이고 판결/반론 타임아웃은 120초입니다. 긴 에이전트 작업을 비동기 job + polling/SSE로 제공할지는 추후 합의해야 합니다. 실제 API 모드에서 프론트가 임의 진행률을 표시하지 않습니다. 화면 이탈/취소는 클라이언트 요청을 중단하지만 서버의 모델 작업까지 취소됐다는 보장은 없습니다.

## 연결 작업 순서와 오류

1. 현재 기능형식과 백엔드 스키마를 합의하고 나의 감정 API, 판결 API, 반론 API를 구현합니다.
2. `src/api/features.ts`에서 실제 경로/필드를 화면 타입으로 매핑합니다. UI용 `source`는 서버에서 받지 않고 어댑터가 붙입니다.
3. 실사용자 ID, 방 ID, 문맥 보관/추세 계산, 인증을 연결합니다.
4. 서버 응답 및 실패/취소를 검증한 뒤 `EXPO_PUBLIC_FEATURE_MODE=api`로 전환하고 앱을 완전히 새로고침합니다.

HTTP 실패/타임아웃 시 입력과 이전 판결을 보관하고 재시도를 제공합니다. 순화 실패 시 원문을 직접 선택할 수 있으며 자동 전송은 없습니다. 온도계는 오류와 재확인 버튼을 표시합니다. 판결은 같은 요청으로 재시도하거나 내용 수정/이전 결과 보기가 가능합니다. 중복 전송·중복 판결 요청을 막고 취소된 응답을 화면에 적용하지 않습니다.

기존 백엔드 엔드포인트, CORS, 휴대폰 연결 주소는 [API 연결 문서](api-integration.md)를 참고하세요. 이 UI 구현에서는 백엔드의 모델 동작이나 API 스키마를 변경하지 않았습니다.
