# KU래쪄용 백엔드 구현 인계와 협의 가이드

이 문서는 프론트 UI를 실제 AI 기능에 연결할 백엔드 팀원을 위한 인계 자료입니다. 먼저 현재 동작과 미구현 범위를 확인하고, 협의 표에서 계약을 정한 뒤 기능별 API를 구현하세요. Codex나 Claude Code에는 [구현 요청문](backend-agent-prompt.md)을 전달하면 됩니다.

기준일은 2026년 10월 3일입니다. 코드 확인 기준은 `backend/app/`과 `frontend/src/`입니다. 아래의 **현재 구현**, **사용자 요구**, **협의 필요**, **추천안**은 서로 구분하며, 추천안을 팀의 최종 결정으로 간주하지 않습니다.

## 읽는 순서

팀원에게 보낼 메시지와 현재 상태 요약은 [백엔드 팀 전달 문서](../backend/docs/team-handoff.md), 감정·순화 판단의 모델 후보는 [Jev 도입 검토](../backend/docs/jev-integration-proposal.md)를 참고하세요. Jev는 도입 가능한 후보이며 현재 코드에는 적용되어 있지 않습니다. 이 검토안이 기존 구현 순서나 팀의 모델 선택을 확정하지는 않습니다.

1. 이 문서에서 요구사항과 협의 항목을 확인합니다.
2. [세 기능 API 문서](frontend-features-api.md)에서 JSON 응답 예시와 화면 흐름을 확인합니다.
3. [기존 API 연결 문서](api-integration.md)와 실제 요청·응답 타입을 대조합니다.
4. [구현 요청문](backend-agent-prompt.md)을 코딩 에이전트에 붙여넣고 단계별로 구현합니다.

[원래 프론트 핸드오프](frontend-handoff.md)는 발표자료에 기반한 초기 구상입니다. 그 문서의 `/analyze`, `/verdict`, 상대 감정 표시, PostgreSQL·LangGraph 계획이 현재 구현됐다는 뜻은 아닙니다. 현재 사용자는 **나의 감정만 표시**하도록 요청했습니다. 원문과 현재 코드가 다르면 이 문서의 상태 설명과 코드를 우선 확인하세요.

## 사용자 요구와 현재 프론트 동작

| 기능 | 사용자 요구 | 현재 준비된 프론트 |
|---|---|---|
| 다툼판결 | 버튼을 누르면 별도 화면에서 진행 | `/verdict`에서 요청 내용 확인, 진행 표시, 양쪽 점수, 요약, 공개 토론 로그, 반론 |
| 언어순화 | ON/OFF, 입력 중 필요하다고 판단되면 대안 제시 | 나(A)의 초안 확인, 대안 선택, 원문 전송, 직접 수정 |
| 감정온도계 | ON/OFF, 진행 중인 대화를 바탕으로 현재 사용자 나의 감정 표시 | 나(A)의 1~5 단계, 추세, 쿨다운 제안 |

현재 프론트 규칙은 다음과 같습니다. 숫자 범위와 정책을 바꾸려면 프론트 계약도 함께 수정해야 합니다.

- 나의 시연 화자는 A, 상대의 시연 화자는 B입니다. 웹의 휴대폰 프레임 밖 관리자 패널에서 A/B를 전환하며 같은 기기에서 상대 발화를 넣습니다. 예시 불러오기·초안 넣기·대화 초기화·서버 연결 확인도 이 패널에 있습니다.
- 초안은 최대 2000자이며 입력이 600ms 멈추면 순화를 확인합니다. 전송 버튼에서도 확인하고 사용자가 선택한 최종 문장만 전송합니다.
- 순화 OFF 또는 상대(B)의 시연 입력에는 초안 분석을 요청하지 않습니다.
- 온도계는 전송된 메시지나 관계가 바뀔 때 최근 최대 10개 메시지로 나(A)를 분석합니다. 아직 전송하지 않은 초안은 포함하지 않습니다.
- 온도계 OFF면 표시와 분석 요청을 중단합니다. 순화와 온도계 토글은 독립입니다.
- 토글과 민감도 설정은 프론트에만 보관합니다. 현재 API에는 토글을 보내지 않으며, 순화 민감도도 어댑터에서 제외합니다. 서버에 설정을 저장하려면 별도 계약이 필요합니다.
- 3단계 이상에서는 쿨다운을 제안합니다. 3분 타이머 종료 후 자동 전송하지 않습니다.
- 판결은 명시적 요청에만 실행합니다. 요청 시점의 최근 최대 10개 메시지를 고정하며 A와 B의 발화가 모두 있어야 버튼을 사용할 수 있습니다.
- 프론트 대화·초안·입력 화자·설정·판결은 메모리에만 있습니다. 새로고침하면 초기화되고 다른 기기로 전달되지 않습니다.

웹 UI는 440×956 논리 크기의 iPhone 18 Pro Max 미리보기를 창에 맞춰 축소합니다. 관리자 패널은 앱 밖에 있고 실제 모바일 앱에는 없습니다. 관리 도구 이동으로 API 계약이 바뀌지는 않으며 관리자 인증/권한 API가 추가된 것도 아닙니다.

## 현재 백엔드와 구현이 필요한 부분

| API | 현재 상태 | 추가 작업 |
|---|---|---|
| `GET /health` | 구현됨, 키 없이 상태 확인 | 기존 동작 유지. AI 키나 모델 기능의 정상 여부를 보장하지 않음 |
| `POST /v1/demo/messages` | 구현됨, 입력 검증·반환 | 기존 입력 전달 시연 유지. 저장이나 채팅 전송 API가 아님 |
| `POST /v1/messages/analyze` | 구현됨, 발화 신호와 대화 전체 갈등 온도 | 기존 기능 유지. 나의 감정으로 재해석하지 않음 |
| `POST /v1/drafts/analyze` | 구현됨, 필요 시 순화문 최대 1개 | 대안 여러 개·민감도 적용 여부 협의 |
| `POST /v1/emotions/analyze` | **미구현**, 프론트에 제안 경로만 있음 | 대상 사용자 감정과 추세 분석 |
| `POST /v1/verdicts` | **미구현**, 프론트에 제안 경로만 있음 | 판결 생성, 요청 대화와 결과 보관 |
| `POST /v1/verdicts/{verdictId}/appeals` | **미구현**, 프론트에 제안 경로만 있음 | 기존 판결 조회, 반론을 포함한 재판결 |

백엔드는 현재 FastAPI와 Pydantic을 사용하고, `OpenAIProvider`에서 모델을 호출합니다. DB, 사용자 인증, 방 관리, 나의 감정 분석, 판결 에이전트는 없습니다. 기존 메시지·초안 분석은 요청에 포함된 최근 대화와 이전 온도를 사용하는 방식이며 서버가 이를 보관하지 않습니다.

**모델 도입 검토:** Jev로 개인 감정 단계나 순화 필요 여부를 판단하고 GPT로 대안 문장·판결 설명을 생성하는 역할 분리를 제안합니다. 분석 인터페이스, 키 의존성, 점수·신뢰도 변환, 설명문 처리와 한국어 비교 평가가 필요합니다. Jev는 새 API나 저장소를 대신 구현해주지 않습니다. 상세한 제안과 미정 항목은 [Jev 검토 문서](../backend/docs/jev-integration-proposal.md)에 있습니다.

기존 요청은 정의하지 않은 필드를 거절하는 `extra="forbid"` 방식입니다. 새 필드를 프론트에서 먼저 보내면 422가 발생합니다. 현재 백엔드 `speaker`는 1~40자의 문자열을 허용하지만 프론트는 A/B만 사용합니다. 이 차이도 실제 사용자 ID 연결 시 고려하세요.

| 판결 공개 대상 | 현재 요청한 앱에서만 표시 | 요청자 화면부터 연결. 상대 공유는 별도 결정 | 판결 조회·채팅 이벤트 |

| 호출 비용과 제한 | 초안 정지마다 분석, 메시지마다 감정 갱신 가능 | 디바운스·캐시·최대 실행시간·라운드 수 합의 | 훅·서버 캐시·에이전트 실행 |

Light 단일 호출을 선택한다면 단순히 두 API를 합치는 것으로 끝나지 않습니다. **전송 전 초안의 감정**과 **사용자가 최종 선택해 전송한 문장의 감정**을 구분하고, 토글 하나만 켜진 경우의 요청도 정의해야 합니다. 현재 프론트는 순화 후 선택한 문장으로 다시 대화 상태를 갱신합니다.

## 기능별 API 구현 가이드

이 절은 **현재 프론트와 연결하기 위한 임시 계약**입니다. 새 감정·판결·반론 API는 아직 없으며 아래 형식은 최종 합의 대상입니다. 서버가 다른 형식을 선택하면 `frontend/src/api/features.ts`에서 화면 타입으로 변환하세요. 현재 어댑터는 `source`를 직접 붙이므로 서버 응답에 넣을 필요가 없습니다.

### 언어순화 기존 API 유지

요청 예시는 [draft-request.json](examples/draft-request.json)입니다. `recent_messages`에는 분석할 초안을 제외한 직전 발화만 넣습니다. `previous_temperature`는 기존의 **대화 전체 갈등 온도**이고, local/receipt 시연에서는 초기값 0으로 유지됩니다.

현재 응답 필드는 `features`, `draft_risk`, `current_temperature`, `threshold`, `decision`, `rewritten_text`입니다. `features`의 범위는 `backend/app/schemas.py`를 기준으로 유지합니다.

| 서버 decision | 프론트 decision | 현재 UI 동작 |
|---|---|---|
| `rewrite_suggested` | `suggested` | `rewritten_text`가 있으면 대안 1개 표시 |
| `below_threshold` | `safe` | 최종 전송 진행 |
| `low_confidence` | `uncertain` | 판단 불확실 안내와 원문/직접 수정 선택 |

초안 확인은 메시지를 저장·전송하거나 대화 온도를 갱신하지 않아야 합니다. 현재 `suggest_rewrite=false`는 필요 여부만 판단하며 순화문을 생성하지 않습니다. 이 동작을 보존하세요. 순화는 불만·요청·경계를 유지하며 없던 사과·사실·약속을 만들지 않아야 합니다.

**확장 추천안:** 기존 `rewritten_text`를 남기고 `alternatives: string[]`를 추가합니다. `sensitivity`도 선택 필드로 추가해 이전 요청을 계속 받을 수 있게 합니다. 서버만 배열을 추가하면 현재 프론트는 여전히 단일 문장만 표시하므로 어댑터가 배열을 우선 사용하고, 배열이 없으면 `rewritten_text`를 사용하도록 함께 수정해야 합니다. 민감도를 서버가 처리하게 된 뒤에만 어댑터에서 전송하세요.

### 나의 감정온도계 제안 API

`POST /v1/emotions/analyze` 요청 예시는 [emotion-request.json](examples/emotion-request.json)입니다.

| 요청 필드 | 형식 | 의미 |
|---|---|---|
| `speaker` | 현재 프론트는 A 또는 B | 감정을 분석할 대상. 현재 화면은 A 요청 |
| `relationship` | 문자열 | 대화 관계 |
| `recent_messages` | `{speaker, text}[]`, 현재 최대 10개 | 이미 전송된 대화. 양쪽 발화와 최신 발화 포함 |

현재 어댑터가 기대하는 응답 예시는 다음과 같습니다.

```json
{
  "subject": "A",
  "level": 3,
  "trend": "up",
  "recommendation": "잠시 쉬면서 내가 원하는 점을 정리해보세요.",
  "contextCount": 4
}
```

`subject`는 요청 `speaker`와 같아야 합니다. `level`은 정수 1~5, `trend`는 `up | flat | down`, `recommendation`은 문자열, `contextCount`는 사용한 메시지 수인 0 이상의 정수입니다. 단계는 평온/주의/경고/위험/폭발에 순서대로 대응합니다.

나의 감정을 기존 `temperature`, `hostility`, 상대의 감정 점수로 대체하지 마세요. 상대 발화는 문맥으로 참고할 수 있지만 응답 대상은 요청한 사용자입니다. 부정적 감정과 공격성도 구분해야 합니다. 현재 예시 온도계는 표현 감지로 동작하며 실제 모델의 평가 기준이나 정확도 검증을 대신하지 않습니다.

현재 요청에는 `previous_emotion`, `room_id`, 메시지 ID가 없습니다. 추세를 DB에서 계산하려면 이 필드를 합의하고 프론트도 바꿔야 합니다. 문맥 부족을 성공 응답으로 표현하려면 현재 필수 `level` 계약에 부족 상태를 추가하는 작업도 필요합니다.

### 다툼판결 제안 API

`POST /v1/verdicts` 요청 예시는 [verdict-request.json](examples/verdict-request.json)입니다.

| 요청 필드 | 형식 | 현재 프론트 값 |
|---|---|---|
| `room_id` | 문자열 | `presentation-room` 고정 |
| `requester` | A 또는 B | A 고정 |
| `mode` | `WWE` 또는 `UFC` | 사용자가 선택 |
| `relationship` | 문자열 | 대화방 설정 |
| `recent_messages` | `{speaker, text}[]` | 요청 시점 최대 10개. 양쪽 발화 포함 |
| `context` | 문자열 | 선택 추가 상황. 빈 문자열 가능, UI 최대 1000자 |

응답 전체 JSON은 [세 기능 API 문서](frontend-features-api.md)의 판결 절에 있습니다. 현재 화면에 필요한 필드는 다음과 같습니다.

| 응답 필드 | 형식과 범위 | 사용 위치 |
|---|---|---|
| `verdictId` | 비어 있지 않은 문자열 | 후속 반론의 조회 키 |
| `mode` | `WWE` 또는 `UFC`, 요청과 일치하도록 구현 | 결과 표시 |
| `plaintiff` | 아래 SideScore | 나(A)의 점수 카드 |
| `defendant` | 아래 SideScore | 상대(B)의 점수 카드 |
| `summary` | 문자열 | 양쪽 입장을 정리한 요약 |
| `recommendation` | 문자열 | 다음 대화를 위한 제안 |
| `humor` | 문자열 | 한 줄 문구. 정책상 생략하면 빈 문자열 |
| `debateLog` | DebateEntry 배열. 로그가 없으면 빈 배열 | 공개 토론 로그 |

SideScore는 `logic`, `emotionControl`, `evidence`를 0~100의 유한한 숫자로 받고, `strength`, `improvement`를 문자열로 받습니다. DebateEntry는 `role`이 `prosecutor | defense | factcheck | judge`, `round`가 1 이상의 정수, `text`가 공개 설명 문자열입니다.

현재 `plaintiff=A`, `defendant=B`는 **화면상의 고정 매핑**입니다. 요청자가 B가 되는 실사용자 환경에서는 반환 대상과 화면 매핑을 함께 합의하세요. 모델이 카드의 대상 사용자를 임의로 뒤집지 않게 해야 합니다. 로그에는 사용자에게 공개할 역할별 의견만 넣으며 모델 내부 추론 기록은 필요하지 않습니다.

**서비스 구현 추천안:** 요청 검증 → 대화 스냅샷 고정 → 검사/변호사/팩트체크/판사 역할별 처리 → 구조화 결과 검증 → 저장 → 응답 순서로 나눕니다. 실제 멀티에이전트 구성과 라운드 정지 기준은 AI 팀이 결정합니다. LangGraph는 계획에 포함되어 있으나 현재 의존성은 아니므로 도입 여부와 버전을 따로 결정하세요.

기본 응답형은 한 번의 요청에 전체 판결을 반환하는 방식입니다. 프론트는 최대 120초를 기다리며 실제 API 모드에는 임의 진행률이 없습니다. 비동기 작업을 도입해 `202 + job_id`를 반환하려면 작업 조회 경로, 완료/실패 상태, 진행 이벤트와 취소 API를 함께 정의하고 프론트도 수정해야 합니다. 현재 어댑터는 202 작업 응답을 판결 결과로 처리할 수 없습니다.

### 반론과 재판결 제안 API

`POST /v1/verdicts/{verdictId}/appeals` 요청 예시는 [appeal-request.json](examples/appeal-request.json)입니다. 본문에는 `text`만 보내며 UI 최대 2000자입니다. 응답은 판결과 같은 형식입니다.

서버는 판결 ID로 원래 요청의 대화·추가 상황·모드·결과를 조회해야 합니다. 현재 프론트는 API 반론 요청에 원래 대화를 다시 보내지 않습니다. 반론 후에도 최초 대화 스냅샷을 유지하고 새로운 채팅 발화를 몰래 섞지 마세요.

**저장 추천안:** 판결 ID, 방/요청자, 요청 스냅샷, 결과, 생성 시각, 부모 판결 ID, 반론 이력을 보관합니다. 새 재판결 ID를 발급한다면 원래 판결과의 연결을 유지하세요. 저장 기간, 반론 누적/횟수, 재시작 시 복구, 다른 사용자의 조회 권한은 협의 항목입니다. 메모리 저장만 쓰면 `uvicorn --reload`나 서버 재시작 후 ID 조회가 실패할 수 있습니다.

## 구현 순서와 완료 기준

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| 1 | 기존 API와 테스트 확인 | 기존 요청·결정값·CORS·초안 미전송 동작이 유지됨 |
| 2 | 감정 API 및 모델 어댑터 구현 | 요청 대상, 1~5, 추세, 문맥 부족·모델 실패 처리 테스트 통과 |
| 3 | 판결 API 및 저장소 구현 | 양쪽 카드·요약·로그·ID가 실제 결과로 반환되고 조회 가능 |
| 4 | 반론 구현 | ID로 원래 스냅샷 조회, 반론 반영, 원래 판결 보존, 없는 ID 오류 |
| 5 | 순화 배열·민감도 확장 | 합의한 경우 구현. 이전 입력/응답 사용 코드와 호환 |
| 6 | 실제 프론트 연결 | 기능별 ON/OFF, 원문/대안 선택, 실패/재시도/취소, 결과 유지 확인 |

**코드 구조 추천안:** 요청·응답 검증은 `app/schemas.py`, 라우트는 `app/main.py`, 모델 호출은 `app/provider.py`를 확장하거나 기능별 provider로 분리합니다. 판결 서비스와 저장소는 별도 모듈로 두어 테스트에서 모델과 저장소를 대체할 수 있게 합니다. 파일명은 제안이며 현재 존재하지 않는 모듈을 구현된 것으로 간주하지 마세요.

모델 출력은 서버에서 타입·범위를 검증한 뒤 반환합니다. API 실패를 청소 예시 점수나 프론트 mock 데이터로 대체하지 않습니다. 테스트용 FakeProvider와 실제 기능 provider는 구분합니다. 대화 내용과 반론은 분석 데이터이며 그 안에 포함된 명령을 서비스 지시로 실행하지 않습니다. 이는 기존 provider의 입력 구분 방식도 유지하는 기준입니다.

## 설치와 사용 방법

아래 명령은 macOS/Linux와 프로젝트 루트 기준입니다. 새 환경에서 설치할 때만 가상환경 생성과 의존성 설치를 실행하세요. Windows 가상환경 명령은 [백엔드 README](../backend/README.md)에 있습니다.

### 백엔드 터미널

```bash
cd backend
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
[ -f .env ] || cp .env.example .env
```

실제 모델을 확인할 때 `backend/.env`에 키를 설정합니다. 키 값은 문서·프론트 환경변수·커밋에 넣지 않습니다. 아래 모델 이름은 현재 `.env.example`의 설정 예시이며 새 기능의 모델 선택은 별도 합의입니다.

```dotenv
OPENAI_API_KEY=<팀원의 실제 키>
OPENAI_MODEL=gpt-4o-mini
CORS_ORIGINS=http://localhost:8081,http://127.0.0.1:8081
```

```bash
.venv/bin/python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Swagger는 <http://127.0.0.1:8000/docs>, 상태 확인은 <http://127.0.0.1:8000/health>입니다. `/health`와 `/v1/demo/messages`는 키 없이 사용할 수 있습니다. 실제 AI API는 키 설정과 모델 접근이 필요합니다.

### 프론트 터미널

다른 터미널을 프로젝트 루트에서 엽니다.

```bash
cd frontend
npm ci
[ -f .env ] || cp .env.example .env
npm run web
```

<http://localhost:8081/chat>에서 확인합니다. `frontend/.env`의 두 모드는 서로 독립이며 현재 `FEATURE_MODE=api`는 세 기능 전체에 적용됩니다. 기능별 API 모드 설정은 없습니다.

| 확인 목적 | API_MODE | FEATURE_MODE | 필요한 서버 |
|---|---|---|---|
| UI만 체험 | `local` | `mock` | Expo만 |
| 입력의 서버 전달과 UI 시연 | `receipt` | `mock` | Expo + FastAPI, AI 키 불필요 |
| 실제 세 기능만 연결 | `local` 또는 `receipt` | `api` | 필요한 기능 API와 키. 채팅 온도는 갱신되지 않음 |
| 기존 메시지 분석과 실제 세 기능 연결 | `ai` | `api` | 기존/신규 API와 키 모두 필요 |

현재 예시 설정은 `EXPO_PUBLIC_API_URL=http://127.0.0.1:8000`, `EXPO_PUBLIC_API_MODE=local`, `EXPO_PUBLIC_FEATURE_MODE=mock`입니다. 변경한 뒤 앱을 완전히 새로고침하세요. 값이 반영되지 않으면 Expo를 다시 시작합니다. 실제 휴대폰에서는 Mac의 LAN IP를 API 주소로 사용하고 백엔드를 `--host 0.0.0.0`으로 실행합니다. 웹 주소가 달라지면 CORS 허용 origin도 변경하세요.

기능을 하나씩 구현 중일 때는 순화만 확인하려면 온도계를 OFF로 두고 판결 화면에 진입하지 않습니다. 감정만 확인하려면 순화를 OFF로 두고 전송된 대화를 만듭니다. 판결만 확인하려면 두 토글을 OFF로 두고 양쪽 발화를 만든 뒤 요청합니다. **예시 대화 불러오기는 두 토글을 ON으로 바꾸므로**, 미구현 기능의 오류가 보일 수 있습니다.

## 오류 계약과 검증 방법

기존 프론트는 오류 응답의 `detail`이 문자열이면 표시하고, 그 외에는 HTTP 상태 코드로 안내합니다. 성공 응답은 JSON이어야 합니다.

| 상황 | 현재 상태 또는 신규 추천안 | 구현 시 확인 |
|---|---|---|
| 입력 오류 | 기존 422 | 공백, 길이·범위 초과, 미합의 필드 검증 |
| 키 없음 | 기존 503 | 모델 호출 전 안내, 예시 성공 응답으로 대체하지 않음 |
| 모델/출력 검증 실패 | 기존 502 | 유효하지 않은 점수·역할·빈 결과를 성공으로 반환하지 않음 |
| 없는 판결 ID | 신규 추천 404 | 다른 스냅샷으로 임의 재판결하지 않음 |
| 분석 가능한 문맥 부족 | 신규 상태 코드·detail 합의 필요 | 온도계 대상 발화 없음, 판결 양쪽 발화 없음 |
| 요청 제한 | 필요 시 429 계약 추가 | 자동 재시도 폭주 방지, 사용자 안내 |
| 대기 시간 초과 | 클라이언트 제한, 서버 정책 협의 | 연결 확인 5초, 순화·감정·메시지 70초, 판결·반론 120초 |

초안 변경·순화 OFF·채팅 화면 이탈 시 초안 확인 요청을 취소합니다. 감정 요청은 온도계 OFF나 분석 입력 변경 시 취소하며, Context에서 관리하므로 채팅 화면을 나갔다는 이유만으로 중단하지는 않습니다. 판결 요청은 판결 화면 이탈이나 취소 버튼으로 중단합니다. 취소된 응답은 화면에 적용하지 않지만 서버의 모델 작업까지 취소됐다는 뜻은 아닙니다. 판결/반론 저장의 중복을 줄이려면 요청 ID와 재시도 중복 처리도 합의하세요.

기존 검증 명령은 다음과 같습니다. 문서 예시나 테스트 확인을 위해 실제 모델 호출을 자동으로 실행하지 않습니다.

```bash
cd backend
.venv/bin/python -m unittest discover -s tests -v
```

다른 터미널의 프로젝트 루트에서 실행합니다.

```bash
cd frontend
npm run typecheck
npm run lint
npm test
npm run build:web
```

현재 백엔드 15개 테스트는 기존 분석/입력 전달/검증/CORS 등을 다루고, 프론트 5개 테스트는 예시 기능과 취소 동작을 다룹니다. **신규 실제 API가 검증됐다는 뜻은 아닙니다.** 구현 시 아래 항목을 추가로 확인하세요.

- 감정 API: 대상 A/B 일치, 1~5/추세 범위, 문맥 부족, 기존 갈등 온도와 분리, 모델 실패.
- 판결 API: 양쪽 발화, 점수 범위, 모드 유지, 공개 로그 역할, ID 저장과 조회, 시간 제한.
- 반론 API: 실제 ID 조회, 원래 대화 유지, 추가 반론 반영, 없는 ID, 원래 결과 보존.
- 순화 확장: 이전 요청 호환, `suggest_rewrite=false`, 저신뢰 판단, 대안 개수/길이, 민감도 범위.
- 프론트 연결: OFF에서 해당 호출 없음, 원문/대안 선택 후에만 전송, 실패 시 입력 유지, 재시도, 늦은 응답 무시, 쿨다운 자동 전송 없음.

테스트에서는 provider와 저장소를 대체해 키 없이 계약을 검증하고, 실제 모델 평가에는 별도 사례와 수동 실행 절차를 사용합니다. 한두 번의 성공 응답이나 고정 예시 테스트만으로 모델의 감정·판결 품질을 검증했다고 보고하지 않습니다.

## 인계 시 남길 기록

구현한 팀원은 변경한 경로/필드, 협의 표에서 선택한 정책과 남은 미정 항목, 실행한 테스트, 실제 모델 호출 여부, 저장소와 재시작 동작을 기록하세요. API 계약이 바뀌면 이 문서와 `frontend-features-api.md`, 프론트 타입/어댑터를 함께 갱신합니다.

이 문서 작성으로 새 API가 구현되거나 팀 계약이 확정된 것은 아닙니다. 현재 앱 기본 모드는 계속 `local + mock`입니다.
