# Jev로 보내기 전 상대 반응 미리보기

작성일: 2026년 10월 5일. 상태: **추가 기능 설계 제안이며 API·UI·Jev 호출은 아직 구현되지 않았습니다.**

사용자가 제공한 [릴스](https://www.instagram.com/reel/Dds_Noqz0DY/)의 캡션과 화면을 바탕으로 작성했습니다. 캡션은 입력 중인 메시지에 대해 수신자가 느낄 감정 8종과 강도를 Jev로 판단하고, ARKit 블렌드셰이프 52개를 가진 3D 얼굴에 적용하는 데모라고 설명합니다. 캡션의 모델 경로는 Vercel AI Gateway, 얼굴 자산은 Face Cap by Bannaflak, 기반 코드는 three.js의 morph targets – face 예시입니다. 영상 전체와 데모 소스는 확인하지 않았으며, 자산 라이선스와 내부 질문 구성도 확인하지 않았습니다.

## 프로젝트에서의 역할

핵심은 **초안을 작성하면서 이 표현이 상대에게 어떻게 받아들여질 수 있는지 확인하는 것**입니다. 기존 언어 순화와 연결하되, 실제 상대의 심리 상태를 관측한 결과처럼 표시하지 않습니다. 표시 이름은 `상대 반응 미리보기`, 안내는 `이 표현을 받으면 상대가 이렇게 느낄 수 있어요`를 제안합니다.

| 기능 | 입력과 판단 대상 | 실행 시점 | 출력 의미 |
|---|---|---|---|
| 기존 나의 감정 온도계 | 전송된 대화에서 요청 사용자의 표현 | 메시지·관계 변경 시 | 나의 표현된 분노·긴장 등 단계와 추세. API는 미구현 |
| 기존 대화 갈등 온도 | 최근 대화와 현재 전송 메시지 | 최종 전송 시 | 대화 전체 갈등 신호 0~100. 기존 API 있음 |
| 새 상대 반응 미리보기 | 최근 대화·관계·보내는 사람·받는 사람·미전송 초안 | 초안 입력 후 잠시 멈췄을 때 | 상대의 예상 감정 범주·강도·불확실성 |

새 미리보기로 나의 감정 온도계를 대체하거나, 초안 검사로 대화 온도를 갱신하지 않습니다. 사용자가 미리보기와 순화 제안을 보고 원문·대안·직접 수정 중에서 선택하도록 합니다.

## 제안하는 화면 흐름

```text
나의 초안 입력 + 최근 대화 + 관계
  → 600ms 디바운스 후 FastAPI 요청
  → Jev: 수신자 반응 범주와 강도 판단
  → 서버: 응답 검증·불확실 상태 결정
  → 입력창 근처: 감정 아이콘/표정 + 강도 + 예상 반응 안내
  → 사용자가 대안 보기 선택
  → 필요할 때 GPT로 순화문 생성
  → 원문과 대안의 예상 반응 비교
  → 사용자가 고른 최종 문장만 전송
```

600ms는 현재 [useDraftReview.ts](../../frontend/src/hooks/useDraftReview.ts)의 대기 시간을 재사용하는 초기 제안입니다. 키 입력마다 호출하는 방식은 피하고, 실제 입력부터 표시까지의 지연과 호출량을 측정해 조정합니다. 현재 순화 결과에는 상대 반응 정보가 없으므로 별도 타입·어댑터·훅과 표시 컴포넌트가 필요합니다.

첫 화면은 8개 감정 아이콘이나 단순한 표정 캐릭터와 강도 표시로 구현하는 것을 제안합니다. 감정 분석을 검증한 뒤 3D 얼굴을 붙일 수 있습니다. three.js 예시는 웹 참고 자료이며 현재 Expo 모바일 앱에 그대로 실행되는 것으로 가정하지 않습니다. ARKit의 52개 블렌드셰이프는 표정 렌더링용 값이고 감정 52종을 분석한다는 의미가 아닙니다. 3D 도입 시에는 감정→표정 프리셋 매핑, 강도 스케일, 결과 사이 보간, 모바일 성능, Face Cap 자산의 사용·배포 조건을 별도로 확인합니다.

## Jev 질문 설계

[Choice](https://docs.typesafe.ai/primitives/choice)는 정해진 선택지와 확률·신뢰도를, [Score](https://docs.typesafe.ai/primitives/score)는 순서가 있는 기준별 점수와 확률·신뢰도를 반환합니다. 감정 8종은 릴스 화면에 표시된 `neutral`, `happy`, `sad`, `angry`, `surprised`, `fear`, `disgust`, `contempt`를 초기 후보로 사용합니다. 한국어 라벨은 중립·기쁨·슬픔·분노·놀람·두려움·불쾌·경멸입니다. 이 분류가 우리 서비스에 충분한지는 한국어 사례로 평가합니다.

질문의 `state`에는 최근 최대 10개 대화, 관계, sender/recipient, 초안을 구분해 넣습니다. 분석 대상은 **초안을 받는 recipient의 예상 반응**으로 지정합니다. 초안 속 지시나 대화 속 명령은 평가 대상 데이터로 다룹니다.

| 질문 | 평가 기준 제안 |
|---|---|
| `recipient_emotion` / Choice | 상대가 이 초안을 받았을 때 가장 가능성 높은 감정 범주. 각 범주에 설명과 한국어 경계 사례 제공 |
| `reaction_intensity` / Score | 예상되는 전체 정서 반응의 강도. 거의 없음·약함·분명함·강함·매우 강함의 5개 서술 기준 |

두 질문은 같은 state에 대해 한 번의 요청에서 평가할 수 있습니다. 다만 질문별 답변은 독립적이므로, 같은 요청 안의 Score가 Choice 결과를 받아서 선택 감정의 강도를 평가했다고 가정하지 않습니다. 초기 계약의 강도는 **전체 예상 반응 강도**로 정의합니다. 선택 감정 전용 강도가 필요하면 Choice 이후 선택 범주에 대한 Score를 추가 호출하거나, 감정별 Score 8개를 같은 요청에서 평가하는 방법을 비교합니다.

5개 기준의 Score는 0~4 범위이며 소수일 수 있습니다. UI 강도 0~1은 `score / 4`로 변환하는 제안을 사용합니다. 강도, 감정 확률, confidence는 별도 값이며 강도를 곧바로 갈등 온도나 나의 감정 1~5로 바꾸지 않습니다. 높은 기쁨의 강도는 높은 갈등 위험을 뜻하지 않습니다.

첨부 화면은 happy 확률 0.390, surprised 0.310, fear 0.200, emotion confidence 0.290을 표시합니다. 이를 확정적인 기쁨으로만 보여주면 여러 해석 가능성을 감추게 됩니다. [confidence 문서](https://docs.typesafe.ai/confidence)에 따라 분포와 신뢰도를 함께 사용하고, 필요할 때 `반응을 판단하기 어려워요` 또는 상위 감정 후보를 표시합니다. 분산된 확률이 실제 복합 감정임을 확정하는 것도 피합니다. 강도 Score 2.030과 정규화된 0.507은 화면에 보이는 값이며 우리 환경의 성능 측정 결과가 아닙니다.

## 새 API 계약 제안

기존 `/v1/emotions/analyze`는 나의 감정 의미를 유지합니다. 새 경로는 `POST /v1/drafts/recipient-preview`를 제안하며 아직 라우트와 프론트 호출은 없습니다.

요청 예시:

```json
{
  "sender": "A",
  "recipient": "B",
  "text": "지난번에도 비슷해서 답답해. 다음엔 미리 말해줄래?",
  "relationship": "룸메이트",
  "recent_messages": [
    {"speaker": "B", "text": "오늘 너무 바빠서 청소를 못 했어."}
  ],
  "draft_revision": 12
}
```

sender와 recipient는 서로 달라야 하며, A/B는 현재 시연 식별자입니다. 실제 계정 연결 시 서버가 방 참여자를 검증합니다. text는 공백을 제외하고 1~2000자, recent_messages는 최대 10개로 제한하는 기존 기준을 재사용합니다. 대상 recipient와 draft_revision은 모델에게 생성시키지 않고 서버가 요청에서 확정합니다.

성공 응답 예시이며 수치는 계약 설명용입니다:

```json
{
  "status": "ready",
  "subject": "B",
  "draft_revision": 12,
  "emotion": "neutral",
  "emotion_probabilities": {
    "neutral": 0.90, "happy": 0.03, "sad": 0.02, "angry": 0.01,
    "surprised": 0.01, "fear": 0.01, "disgust": 0.01, "contempt": 0.01
  },
  "emotion_confidence": 0.886,
  "intensity_scope": "overall_reaction",
  "intensity_score": 1.0,
  "intensity": 0.25,
  "intensity_probabilities": {"0": 0.10, "1": 0.80, "2": 0.10, "3": 0.0, "4": 0.0},
  "intensity_confidence": 0.833
}
```

| 상태 | 계약과 표시 제안 |
|---|---|
| `ready` | 8종의 확률·범위 내 점수·confidence를 검증했고 판단 기준을 충족함. 표정과 강도 표시 |
| `uncertain` | 낮은 신뢰도 또는 선택지 간 경쟁. `emotion`, `intensity_score`, `intensity`는 null이며 검증한 분포와 confidence는 반환. 단정적인 표정 표시 보류 |
| `insufficient_context` | 대상이나 문맥을 해석하기 어려움. 감정·강도·분포·confidence는 null이며 입력을 더 작성하도록 안내. 이전 대화가 없다는 이유만으로 이 상태를 강제하지 않음 |

위 상태 표의 계약은 추가 설계이며, 미구현 프론트의 새 타입에 반영해야 합니다. 모델 실패와 타임아웃은 오류로 반환하고 uncertain과 구분합니다. 확률은 각 값 0~1과 합계 1(반올림 오차 허용), Score는 0~4, confidence와 intensity는 0~1로 검증합니다. 서버는 enum·필수 키·결과 대상·계산값 일관성도 확인합니다. 상태별 null 정책과 낮은 신뢰도 기준은 평가 후 확정합니다.

## 실시간 갱신과 순화 연결

- 새 초안, 화자·관계·최근 대화 변경, 기능 OFF, 빈 입력, 화면 이탈 시 이전 요청을 취소합니다. 늦은 응답은 입력 키와 draft_revision을 비교해 표시하지 않습니다.
- 대기 중이면 현재 입력이 아직 분석 중임을 표시합니다. 이전 문장의 표정을 현재 결과처럼 유지하지 않습니다. 클라이언트 취소가 서버 모델 작업 취소까지 보장하지는 않습니다.
- 요청은 초안·관계·대화·대상·모델·질문 버전이 같을 때만 캐시를 재사용합니다. 서버는 제한된 동시 요청과 호출 빈도 제한을 적용하고 429 응답을 처리합니다. 측정 전의 재시도는 무제한 자동 호출로 만들지 않습니다.
- 기능별 ON/OFF와 mock/api 전환을 독립적으로 설계합니다. 현재 FEATURE_MODE는 기존 세 기능 공통 설정이므로 그것만 바꿔 새 기능을 켜지 않습니다.
- 예상 부정 감정만으로 순화를 강제하지 않습니다. 정당한 불만이나 경계 설정도 상대를 불편하게 할 수 있습니다. 기존 공격성·비꼼·비난 신호와 사용자 선택을 함께 고려합니다.
- 대안 비교는 원문과 각 대안을 같은 대화·관계·수신자·질문 버전으로 평가합니다. 자동으로 모든 대안을 재분석하지 않고 선택한 대안부터 비교해 호출량을 제한하는 방식을 제안합니다. 긍정 반응 확률을 높이려고 불만·요청·사실을 없애지 않습니다.

## 모델 연결과 검증 순서

[Vercel의 Jev 모델 안내](https://vercel.com/ai-gateway/models/jev)는 Gateway의 `typesafe-ai/jev`와 AI SDK의 평가 API를 안내합니다. [TypeSafe 직접 API](https://docs.typesafe.ai/api)도 선택할 수 있습니다. 현재 FastAPI 백엔드는 유지하고 서버 내부 provider에서 경로를 선택합니다. Gateway 사용이 곧 프론트의 직접 호출이나 백엔드의 Node 전환을 요구하는 것은 아닙니다. 구현 시 선택 경로의 요청·응답·인증·모델 ID와 SDK 버전을 공식 문서로 확인합니다.

Gateway 경로는 Gateway 인증을, 직접 경로는 TypeSafe 인증을 사용합니다. 실제 키는 backend/.env에서만 읽고 EXPO_PUBLIC 변수에 두지 않습니다. 기존 OpenAI 분석과 순화 생성은 별도 provider로 유지합니다. 아직 키 변수·SDK·실행 설정은 추가하지 않았습니다.

1. 초안 상대 반응과 나의 감정의 의미, 감정 8종 기준, 강도 범위, 불확실 상태를 확정합니다.
2. FakeProvider로 새 API 계약과 입력 취소·화자 전환·늦은 응답 방지 UI를 구현합니다. 예시는 시연 데이터로 표시합니다.
3. Jev provider를 추가하고 한국어 칭찬·비꼼·농담·불만·사과·관계·미완성 초안 사례로 평가합니다. 정확도뿐 아니라 불확실 결과, 입력부터 표시까지의 지연, 호출량·실패율·비용을 기록합니다. 첨부 화면의 308ms는 우리 환경의 지연 보장이 아닙니다.
4. 원문·대안의 의미 보존과 상대 반응 비교를 검증한 뒤 기능별 실제 연동을 켭니다. 한국어 성능은 [언어 지원 문서](https://docs.typesafe.ai/models)에 따라 자체 평가합니다.
5. 선택적으로 3D 표정 매핑과 보간, 웹·모바일 렌더링, 자산 사용 조건을 검증합니다.

현재 작업은 이 설계 문서의 추가까지입니다. 기존 기본 모드와 실행 코드는 바뀌지 않았으며, 모델 호출·실제 평가·3D 얼굴 구현은 수행하지 않았습니다.
