# 백엔드 팀원에게 전달할 현재 상태와 구현 요청

프론트는 중간 발표에서 세 기능의 흐름을 보여줄 수 있는 상태이며, 실제 기능 API는 기존 갈등 분석과 단일 언어 순화까지만 구현되어 있습니다. 이 문서는 팀원에게 현재 상태를 설명하고 다음 작업과 참고 문서를 전달하기 위한 요약입니다. 확인 기준일은 2026년 10월 3일입니다.

## 바로 전달할 메시지

아래 문구를 팀원에게 복사해서 전달할 수 있습니다.

> 프로젝트를 `backend/`와 `frontend/`로 나눴고, 프론트는 React Native + TypeScript + Expo로 준비했어. 채팅, 언어 순화 ON/OFF와 대안 선택, 나의 감정 온도계 ON/OFF와 쿨다운, 별도 다툼판결 화면과 반론 UI가 있어. 웹에서는 휴대폰 프레임 밖 관리자 패널로 예시 대화와 A/B 입력을 조작할 수 있어.
>
> 현재 화면은 `local + mock` 시연 모드라 결과가 실제 AI 분석은 아니야. 기존 백엔드에는 `/v1/messages/analyze`로 대화 전체 갈등 온도 0~100을 계산하고, `/v1/drafts/analyze`로 순화 필요 여부와 대안 문장 1개를 반환하는 GPT 호출 코드가 있어. 키와 연결 설정을 준비해야 실제 AI 응답을 볼 수 있어.
>
> 추가로 구현해야 하는 건 나 개인의 감정을 반환하는 `/v1/emotions/analyze`, 다툼판결 `/v1/verdicts`, 판결 ID를 조회해서 재판결하는 `/v1/verdicts/{verdictId}/appeals`와 저장소야. 기존 갈등 온도를 개인 감정으로 바꾸어 표시하면 안 돼.
>
> Jev는 감정 단계와 순화 필요 여부 판단에 도입할 수 있는 후보로 검토했어. 아직 적용하거나 실제 한국어 성능을 검증한 건 아니고, Jev가 판단을 맡고 GPT가 대안 문장과 판결 설명을 생성하는 구조를 제안해. 감정 API부터 비교 평가한 뒤 채택 여부를 정하면 좋겠어.
>
> 우선 `backend/docs/team-handoff.md`와 `docs/backend-implementation-handoff.md`를 읽어줘. 모델 검토는 `backend/docs/jev-integration-proposal.md`, 요청·응답은 `docs/frontend-features-api.md`, Codex나 Claude Code에 맡길 작업은 `docs/backend-agent-prompt.md`에 정리했어. API 형식이나 모델 정책을 바꿀 부분을 같이 정한 뒤 기능별로 연결하자.

## 구현 상태

| 구분 | 준비된 내용 | 추가로 필요한 내용 |
|---|---|---|
| 프론트 | 채팅과 세 기능 UI, 예시 데이터, API 호출 어댑터 | 실제 응답 연결, 합의한 API 변경 반영 |
| 백엔드 기존 기능 | 상태 확인, 입력 수신 시연, 갈등 분석, 순화문 최대 1개 | 실제 키·모델 응답과 프론트 연결 확인 |
| 개인 감정 | 프론트에 1~5 단계·추세·안내 표시와 API 초안 | 대상 사용자 분석 API, 평가 기준, 문맥 부족·추세 처리 |
| 다툼판결과 반론 | 요청·결과·공개 토론 로그·반론 화면과 API 초안 | 생성 API, 판결 스냅샷과 결과 저장, ID 조회·재판결 |
| Jev | 도입 검토 문서 | 모델 선택, 호출 모듈, 응답 변환, 한국어 비교 평가 |
| 실제 사용자 간 채팅 | 같은 화면에서 A/B 입력 시연 | 인증, 방 관리, 저장, 다른 기기로 메시지 전달 |

FastAPI와 OpenAI 호출 코드가 있으며 PostgreSQL·LangGraph는 아직 의존성이나 실행 기능으로 구현되어 있지 않습니다. 프론트 상태는 메모리에만 있어서 새로고침 시 초기화됩니다.

## 먼저 협의할 내용

- **API 형식:** 프론트의 `/v1/...` 임시 계약으로 먼저 연결할지 결정합니다. 기존 `/v1/messages/analyze`와 `/v1/drafts/analyze`는 보존합니다.
- **감정 의미와 모델:** 나의 분노·긴장 등 표시 대상, 1~5 단계 기준, 추세, 문맥 부족 처리를 정합니다. Jev는 후보이며 감정 API 자체는 별도로 필요합니다.
- **순화 정책:** 현재 1개 대안을 유지할지 최대 3개로 늘릴지, UI 민감도와 관계 설정을 어떻게 반영할지 정합니다.
- **판결 정책과 저장:** WWE/UFC 차이, 역할별 처리, 최대 실행시간, 공개 설명, 저장소와 반론 이력을 정합니다.
- **연결 범위:** 중간 발표까지 실제로 연결할 기능과 후속 구현을 구분합니다. 새 기능 전체를 한 번에 API 모드로 켜면 미구현 경로에서 오류가 납니다.

## 추천 작업 순서

1. 기존 API와 테스트를 확인하고 프론트 입력 전달을 확인합니다.
2. 개인 감정 API를 구현하면서 GPT와 Jev를 비교할 수 있는 분석 구조를 준비합니다. Jev 채택은 평가 후 결정합니다.
3. 판결 API와 저장소를 구현한 뒤 반론 API를 연결합니다.
4. 합의한 순화 대안 수·민감도 정책을 반영합니다. Jev로 순화 판단을 바꾸는 작업은 별도 평가 후 진행합니다.
5. 기능별 실제 API를 연결하고 ON/OFF·오류·취소·원문과 대안 선택을 확인합니다.

기존 언어 순화는 신규 API 구현 전에 실제 연결을 확인할 수 있습니다. 감정·판결까지 모두 API 모드로 켜야 한다는 뜻은 아닙니다.

## 시연과 실제 연결 확인

프로젝트 루트 기준으로 서로 다른 터미널에서 실행합니다. 새로 클론했다면 README의 설치 단계를 먼저 진행합니다.

```bash
cd backend
.venv/bin/python -m uvicorn app.main:app --reload --port 8000
```

```bash
cd frontend
npm run web
```

웹은 <http://localhost:8081/chat>, API 문서는 <http://127.0.0.1:8000/docs>입니다. 실제 휴대폰에서는 `localhost` 대신 개발 PC의 LAN IP를 사용해야 합니다.

| 확인 목적 | 프론트 설정 | 현재 확인 가능한 범위 |
|---|---|---|
| UI 시연 | `API_MODE=local`, `FEATURE_MODE=mock` | 백엔드 없이 예시 동작 |
| 입력 전달 | `API_MODE=receipt`, `FEATURE_MODE=mock` | `/v1/demo/messages` 수신 확인. AI·저장 없음 |
| 기존 메시지 분석 | `API_MODE=ai`, `FEATURE_MODE=mock` | 기존 대화 갈등 온도 분석. 개인 감정·판결은 예시 |
| 기존 순화만 연결 | `API_MODE=ai`, `FEATURE_MODE=api` | OpenAI 키 준비 후 온도계 OFF, 판결 미사용으로 기존 두 API 확인 |

표의 변수는 `frontend/.env`의 `EXPO_PUBLIC_API_MODE`와 `EXPO_PUBLIC_FEATURE_MODE`를 줄여 쓴 것입니다. `FEATURE_MODE=api`는 세 기능 공통 설정이며 기능별 모드는 없습니다. 예시 대화 버튼은 두 토글을 ON으로 바꾸므로 순화만 확인할 때는 다시 온도계를 OFF로 두세요. 기능 모드 변경 후 앱을 새로고침하고, 반영되지 않으면 Expo를 재시작합니다.

백엔드 키는 `backend/.env`에만 둡니다. `/health` 성공은 AI 키나 신규 기능의 정상 응답을 검증한 것이 아닙니다. Jev 키·설정은 아직 추가되지 않았으며, 이 문서 저장으로 서버 기능이나 기본 시연 모드를 바꾸지 않았습니다.

문서는 현재 로컬 작업 폴더에 작성되어 있습니다. 팀원이 같은 내용을 보려면 변경 파일을 전달하거나 팀의 Git 작업 흐름에 따라 커밋·공유해야 합니다.
