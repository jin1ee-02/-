# Jev 도입 검토와 백엔드 구현 제안

이 문서는 감정 온도계와 언어 순화의 판단에 Jev를 도입할 수 있는지 검토하고, 백엔드 팀원이 구현할 때 필요한 경계와 작업을 정리합니다. **현재 설계에 도입할 수 있지만 아직 적용하지 않았으며, 모델 선택은 팀 협의 사항입니다.** 대안 문장과 판결 설명을 생성하는 역할은 기존 GPT 계열 모델에 남기는 구성을 제안합니다.

확인 기준일은 2026년 10월 3일입니다. 아래의 공식 기능 설명은 TypeSafe 문서에 근거하며, 우리 서비스에 대한 적용 방식과 순서는 제안입니다. 실제 Jev 호출이나 한국어 성능 비교는 수행하지 않았습니다.

2026년 10월 5일 사용자 제공 릴스 캡션·화면을 바탕으로 [보내기 전 상대 반응 미리보기](jev-recipient-preview-proposal.md) 설계를 추가했습니다. 초안으로 수신자의 예상 감정 8종과 강도를 판단하고 순화 대안 비교에 연결하는 제안입니다. 기존 나의 감정 온도계와 별도 기능이며, API·UI·Jev 호출·3D 표정은 아직 구현되지 않았습니다.

## 현재 구현과 도입 범위

현재 [provider.py](../app/provider.py)의 `OpenAIProvider`가 분석과 순화문 생성 모두를 처리합니다. 기본 모델 설정은 `gpt-4o-mini`이며, Jev SDK·호출 모듈·설정은 없습니다. [main.py](../app/main.py)는 이 provider를 직접 의존합니다.

| 기능 | 현재 코드 | Jev 적용 제안 |
|---|---|---|
| 전송된 메시지의 갈등 분석 | GPT가 공격성·비꼼·비난·회복 신호를 평가하고 코드가 대화 갈등 온도 0~100 계산 | 기존 신호 분석을 Jev로 대체하는 실험은 가능. 개인 감정 API를 먼저 평가한 뒤 진행 |
| 초안 언어 순화 | GPT 분석 후 필요할 때 GPT로 순화문 최대 1개 생성 | Jev로 필요 여부를 판단하고, 필요한 초안만 GPT로 문장 생성 |
| 나의 감정 온도계 | 프론트 예시만 있음. `/v1/emotions/analyze` 미구현 | 대상 사용자의 표현에서 드러난 분노·긴장 정도를 Jev로 평가하는 새 API 구현 |
| 초안 상대 반응 미리보기 | 추가 설계 문서만 있음. API·UI 없음 | 수신자의 예상 감정 8종과 전체 반응 강도 평가, 불확실성 표시, 원문·순화 대안 비교 |
| 다툼판결과 반론 | 프론트 예시만 있음. 판결·반론 API와 저장소 미구현 | 초기에는 GPT 기반 구현. Jev의 항목별 평가 보조는 후속 비교 대상으로 검토 |

대화 전체의 갈등 온도와 사용자 개인의 감정 단계는 서로 다른 결과입니다. 기존 `temperature`나 `hostility`를 나의 감정으로 이름만 바꿔 반환하지 않습니다. 감정 온도계가 무엇을 측정할지, 예를 들어 표현된 분노·긴장 정도인지, 팀에서 먼저 정의해야 합니다.

## Jev의 공식 기능

Jev는 TypeSafe AI의 System One 모델입니다. 입력 `state`와 질문 `questions`를 받아 정해진 형식의 판단을 반환하며 자유로운 문장을 생성하지 않습니다. 질문 여러 개를 같은 호출에서 평가할 수 있습니다. [공식 소개](https://docs.typesafe.ai/introduction)

| 질문 형식 | 공식 출력 | 우리 서비스에서 검토할 용도 |
|---|---|---|
| Choice | 선택지, 선택지별 확률, 신뢰도 | 명시한 감정 범주나 처리 경로 선택 |
| Score | 서술한 단계에 대한 점수, 단계별 확률, 신뢰도 | 분노·긴장, 공격성, 비꼼을 각각 평가 |
| Noul | 예라고 판단할 확률 0~1. 별도 confidence 없음 | 공격적 표현 여부처럼 명확히 정의한 예·아니오 조건 평가 |

Score의 단계는 숫자만 쓰지 않고 상황을 설명해야 합니다. 다섯 개 기준을 쓰면 점수는 0~4 범위이며 소수일 수 있습니다. UI의 1~5 정수로 반환하려면 서버에서 변환 정책을 정해야 합니다. [Score 공식 문서](https://docs.typesafe.ai/primitives/score), [Noul 공식 문서](https://docs.typesafe.ai/primitives/noul)

`confidence`는 판단의 확실성을 나타내며 감정의 강도나 사용자의 실제 심리 상태를 확정하는 값이 아닙니다. Noul의 0.8도 감정 강도 80%가 아니라 해당 질문에 예라고 판단할 확률입니다. [Confidence 공식 문서](https://docs.typesafe.ai/confidence), [Noul 해석](https://docs.typesafe.ai/primitives/noul)

## 제안하는 역할 분리

```text
프론트 앱
  → FastAPI의 기존 또는 신규 기능 API
      ├─ 감정 요청 → Jev 판단 → 서버에서 단계·추세·안내 변환
      ├─ 순화 요청 → Jev 판단 → 필요할 때 GPT로 대안 생성
      └─ 판결 요청 → GPT 기반 판결 서비스 → 결과와 대화 스냅샷 저장
  ← 프론트와 합의한 JSON 응답
```

프론트가 TypeSafe나 OpenAI를 직접 호출하지 않습니다. 모델 선택과 응답 변환은 백엔드 내부에서 처리하고, 화면은 기존 API 계약을 사용합니다. 개인 감정·판결·반론 API는 모델을 선택하는 것과 별개로 새로 구현해야 합니다.

**코드 구조 제안:** 분석 provider와 문장 생성 provider의 인터페이스를 분리합니다. Jev용 분석 모듈을 추가하고, 기존 GPT 분석과 비교하거나 설정으로 선택할 수 있게 합니다. 현재 `main.py`가 `OpenAIProvider`와 `OpenAIError`에 의존하므로 서비스가 공통 분석 인터페이스와 공통 오류를 사용하도록 함께 수정해야 합니다. 모델 이름만 바꾸는 연결 방식은 사용할 수 없습니다.

현재의 `get_provider()`는 `OPENAI_API_KEY`가 없으면 503을 반환합니다. Jev만 필요한 감정 API가 이 의존성을 그대로 쓰면 불필요하게 OpenAI 키까지 요구하게 되므로 기능별 의존성도 분리해야 합니다. GPT가 필요한 순화문·판결과 Jev만 사용하는 분석의 키 요구를 각각 정의하세요.

## 감정 온도계 API 구현 제안

대상 API는 `POST /v1/emotions/analyze`이며 현재 프론트의 임시 계약은 [구현 인계 문서](../../docs/backend-implementation-handoff.md)와 [API 상세 문서](../../docs/frontend-features-api.md)를 따릅니다. 요청 예시는 [emotion-request.json](../../docs/examples/emotion-request.json)입니다.

입력은 `speaker`, `relationship`, `recent_messages`입니다. 상대 발화는 문맥으로 참고하되 판단 대상은 요청 `speaker`입니다. `subject`와 메시지 수는 서버가 입력에서 확정하고 계산하며, 모델이 대상 사용자를 바꾸도록 두지 않습니다.

```json
{
  "subject": "A",
  "level": 3,
  "trend": "up",
  "recommendation": "잠시 쉬면서 내가 원하는 점을 정리해보세요.",
  "contextCount": 4
}
```

위 값은 **계약 설명용 예시**이며 실제 분석 응답이 아닙니다. `level`은 1~5 정수, `trend`는 `up | flat | down`, `recommendation`은 문자열, `contextCount`는 사용한 메시지 수입니다. 서버는 이 화면 형식으로 변환한 후 반환합니다.

| 구현 항목 | 제안과 협의 필요 사항 |
|---|---|
| 단계 기준 | 평온·주의·경고·위험·폭발을 구별하는 구체적 발화 기준을 작성. 부정적 감정과 상대를 공격하는 표현을 별도로 평가 |
| 점수 변환 | Jev Score 0~4 소수와 단계별 확률을 어떻게 1~5 정수로 표시할지 합의. 반올림 또는 최빈 단계 등 후보를 사례로 비교 |
| 추세 | 현재 요청에는 이전 감정·방 ID·메시지 ID가 없음. 우선 같은 최근 대화 안의 대상 사용자 앞뒤 발화를 정한 기준으로 각각 평가하고 코드에서 비교하는 방법 검토 |
| 문맥 부족 | 대상 발화 없음·비교할 발화 부족·판단 불확실을 구분. `flat`을 알 수 없음의 대체값으로 쓰지 않음. 오류 또는 상태 확장 정책 합의 |
| 안내 문구 | Jev는 문장을 생성하지 않으므로 검토된 단계별 안내를 서버에서 선택하거나 필요할 때 GPT 호출. 정해진 안내는 개인화된 AI 생성 조언으로 표시하지 않음 |
| 신뢰도 | 낮은 신뢰도에서 보류·GPT 재평가·문맥 부족 안내 중 정책 결정. 프론트에 새로운 상태나 필드를 쓰면 타입·어댑터도 함께 수정 |

모델에 감정 평가와 메시지 개수 세기를 한꺼번에 맡기지 않습니다. 단계 평가만 모델에 맡기고 개수, 추세 비교, 범위 검사, 상태 갱신은 코드에서 처리하는 구성을 제안합니다.

## 기존 언어 순화 API의 호환 작업

기존 `POST /v1/drafts/analyze`와 `suggest_rewrite=false`를 유지합니다. 초안 검사에서 메시지를 전송하거나 대화 온도를 갱신하지 않습니다. 최종 원문 또는 대안 선택은 사용자에게 남깁니다.

| 현재 계약 | Jev 도입 시 필요한 처리 |
|---|---|
| hostility·sarcasm·blame·repair 정수 0~4 | 각 신호를 별도 기준으로 평가하고 정수 변환 정책 정의. 기존 계산 가중치는 검증된 확률이 아니므로 비교 평가 |
| escalation_delta 정수 -2~2 | 최근 문맥 대비 변화 기준을 작성하고 모델 결과를 서버에서 범위 검사 |
| confidence 정수 0~4 | Jev의 Choice·Score confidence는 0~1이며 현재 GPT의 자기평가와 의미도 다름. 단순 배율만 적용해 같은 기준이라고 가정하지 않고 변환·통합·보류 기준을 사례로 검증 |
| rationale 문자열 | Jev는 설명문을 생성하지 않음. 선택된 신호를 바탕으로 서버의 정해진 설명을 만들거나 별도 GPT 설명을 사용. 이를 Jev가 생성한 근거라고 표시하지 않음 |
| rewritten_text 문자열 또는 null | 판단 후 GPT로 생성. 현재 단일 대안을 유지하고 배열 확장은 별도 합의 |
| low_confidence 결정값 | Jev 불확실성의 보류 기준을 정해 기존 화면의 불확실 상태로 변환 |

`Noul`로 순화 필요 여부를 바로 판단하는 경로도 후보입니다. 다만 이 경우 기존 `features`, 위험도 계산, 민감도, 신뢰도 처리를 어떻게 유지할지 먼저 설계해야 합니다. 두 판단 경로를 동시에 임의 적용하지 않습니다.

## 구현 순서와 평가 기준

1. 기존 API와 테스트를 유지하고, 개인 감정의 의미·단계 기준·문맥 부족·추세 정책을 합의합니다.
2. 감정 API와 모델을 대체할 수 있는 인터페이스를 구현합니다. FakeProvider로 요청 대상·범위·오류 계약부터 확인합니다.
3. 별도 Jev 분석 모듈과 서버 응답 변환을 구현합니다. 동일한 사례를 평가할 GPT 비교 경로를 준비합니다.
4. 팀이 실제 평가를 실행할 때 한국어 대화에서 정확도, 불확실성, 응답시간, 호출 비용을 비교합니다. 평가 입력과 기대 결과는 별도로 작성합니다.
5. 결과를 보고 Jev 채택 여부를 정하고, 감정 API부터 프론트에 연결합니다. 이후 언어 순화 판단의 교체 여부를 결정합니다.
6. 판결·반론·저장소는 별도 기능으로 구현합니다. Jev 채택 여부가 이 작업 전체를 막지 않도록 합니다.

평가 사례에는 진짜 칭찬과 비꼼, 친한 사이의 농담, 욕설 없는 비난, 정당한 불만, 사과, 화자 전환, 문맥 부족을 포함합니다. 기존 [eval_cases.json](../examples/eval_cases.json)은 갈등 신호 사례이므로 개인 감정의 정답 데이터로 그대로 쓰지 않습니다.

TypeSafe는 영어에서 정확도가 가장 높고 다른 언어는 동일하지 않다고 설명합니다. 한국어 채팅에서 GPT보다 정확하거나 빠르다고 아직 결론 내릴 수 없습니다. [언어 지원 안내](https://docs.typesafe.ai/models) 또한 공식 문서는 문자 그대로의 해석, 복잡한 간접 추론, 계산 등에 한계가 있다고 설명합니다. [알려진 한계](https://docs.typesafe.ai/model-jaggedness/jev-1.13)

## 설정과 팀 결정

TypeSafe 호출에는 별도 키가 필요합니다. 구현 시 키는 `backend/.env`에서만 읽고 `.env.example`에는 키 이름과 빈 예시만 기록합니다. 현재 `.env.example`에는 Jev 설정을 추가하지 않았습니다. 모델 버전·SDK·설정 이름은 구현 시 공식 문서와 설치 버전을 확인해 선택하세요. 평가 결과에는 실제 응답 모델 버전을 기록합니다. [공식 모델 안내](https://docs.typesafe.ai/models), [API 안내](https://docs.typesafe.ai/api)

| 결정할 내용 | 현재 상태 |
|---|---|
| Jev 채택과 적용 기능 | 검토안. 감정 온도계부터 비교하는 방식 제안 |
| 한국어 단계 기준과 정수 변환 | 미정 |
| 저신뢰·문맥 부족 시 응답 | 미정. 기존 프론트 계약과 함께 결정 |
| 추세 계산과 상태 저장 | 미정. 현재 요청에는 이전 감정과 실제 방 ID 없음 |
| 안내 문구와 rationale 생성 방식 | 정해진 문구 또는 GPT 사용 여부 미정 |
| 실제 평가 실행과 담당자 | 미정. 아직 유료 모델 호출하지 않음 |

이 문서를 코딩 에이전트에 전달할 때는 [백엔드 구현 요청문](../../docs/backend-agent-prompt.md)에 채택한 모델 정책과 구현 범위를 덧붙입니다. Jev 도입이 합의되지 않았다면 기존 GPT 경로를 보존하고 평가용 모듈을 별도로 준비하세요.
